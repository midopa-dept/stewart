## 3. 가설
- **G1**(주, Q1): S − X ≠ 0, X ∈ {M, O, P}(양측). Holm 으로 3개를 보정한다. 판정:
  - CI 하한 > 0 → "S 가 X 보다 낫다"
  - CI 상한 < 0 → "X 가 S 보다 낫다"
  - 90% CI ⊂ ±5%p → "동등"
  - 그 밖 → 보류
- **G2**(보조, 기술 통계): 회차당 벽시계·입력 토큰·단계 수의 S/X 중앙값 비와 과제 군집 CI. 결함 셈(D1–D7)은 어댑터마다 되는 칸만 낸다. 되는 칸 표는 등록 때 붙인다(평가 담당 답 ①: 동료 로그 꼴에 따라 "자료 없음" 칸이 생김).
- **G3**(Q2, 파일럿 — 가설 아님): TB 2.1 파일럿 10과제 × 3회 × {S, terminus-2}. 끝까지 도는 비율, 회차당 시간·돈, 실패 꼴(시간 초과·컨테이너 오류·채점 오류)을 기록한다.
  - P-001 점검 C1(orig × Terminus 가 카드 73.0 ±10)은 10과제·abl-3p 로 판정하지 않는다. 참고만 한다.
  - 본 묶음 크기는 이 분산으로 셈한다(§6).
  - 리더보드 업로드는 끈다(공개는 사람 승인 사항).
  - **실행기 붙이는 꼴(연구 담당 결정 11-12, 평가 담당 물음 — 비공개 운영 기록 §1)**: Harbor 0.25.0 은 opencode·pi·mini_swe_agent·terminus_2 를 "installed agents"로 과제 컨테이너 안에 실행 때 깐다. 그 설정은 맥 쪽 v2.0.6 어댑터와 다르다(재시도·HOME 격리·걸음 상한·망 손잡이). 그래서 실행기마다 나눈다.
    - S(stewart): Harbor 에 없으므로 평가 쪽이 우리 어댑터를 **Harbor 사용자 정의 실행기**로 넣는다(묶음 안 wheel, 설치 없이). 맥 칸 G1 과 같은 실행기 조건이다.
    - terminus-2: **Harbor 기본 그대로**(가) 둔다.
      - 판은 Harbor 0.25.0 과 agent kwarg 로 고정한다.
      - 맞추는 것은 모델 쪽만이다: 끝점·서빙 별칭·max_tokens·temperature·생각 켬. 그 밖의 차이(다시 보내기, 걸음·시간 상한, 망)는 표에 적는다.
      - 까닭: terminus-2 의 값은 TB 의 표준 기준 실행기라는 데 있다. 우리 꼴로 바꾸면 공개 숫자와 잇는 다리를 잃는다. G3 는 판정하지 않는 파일럿이므로 차이를 적는 것으로 충분하다.
      - 표 칸 값(평가 담당이 Harbor 0.25.0 코드를 읽음, 11-12)
        - 다시 보내기: 두 겹이라 차례당 최대 9번이다. terminus_2._query_llm 3번(문맥 초과만 빼고) × lite_llm.call 3번(wait 4–15초, 문맥·출력 길이·인증 오류만 빼고). 끌 kwarg 가 없다 → "끊김 삼킴" 대조(§5 1)를 건다. 다시 보내기 기다림도 과제 시간 상한 안에 든다.

## 4. 지표·분석
- 주 지표: 과제별 성공 비율(회차 평균). 대비마다 과제 군집 부트스트랩 95% CI(B = 10,000, 시드 20261112), TOST 는 90% CI.
- 분석본: P-001 의 x1_analysis.py(a9eb1076)를 실행기 축으로 바꾼 판이다. sha 는 등록 때 넣는다. **등록 전에 가짜 결과 줄로 시험이 통과해야 한다.** 분석은 `PYTHONHASHSEED=0` 으로 고정해 돌리고, 같은 입력으로 두 번 돌려 출력이 바이트까지 같음을 확인한다(P-001 덧붙임 10 교훈). 측정 불가 집계도 처음부터 스크립트로 내고, 그 sha 를 등록한다.
- 빼기 차례는 P-001 §R 그대로다: 측정 불가(§5-1) → 울타리 무효 → 유효 0 과제.
- 한 칸의 측정 불가가 10%를 넘으면 그 대비에 "측정 불가 많음"을 표시한다. 판정은 내되 민감도를 반드시 함께 낸다.

## 5. P-001 교훈으로 고친 조건
1. **요청 상한은 평가 대기열 차례 전달 프록시 한 곳에**(평가 담당 답 ②). 모든 실행기의 모델 요청이 그 프록시를 지나므로 실행기와 무관한 공통층이다.
   - 총 시간 상한: 모든 실행기에 같게 둔다. 값 = max_tokens ÷ 20 tok/s 올림(8192 → 600초). 파일럿 분포로 등록 전에 고친다.
   - idle 상한 60초: 스트리밍 요청에만 걸린다(비스트리밍은 응답 바이트가 끝에 한꺼번에 와서 가를 수 없음).
   - 스트리밍(평가 담당 답 — 비공개 운영 기록, 평가 대기열 v12.44 칸): (앞 판의 글 "S 는 이미 스트리밍이다" — 지움) → **바로잡음(11-12 13시대, 평가 담당 맥 smoke 실측)**: S 는 평가 길에서 **비스트리밍**이다. run 엔진은 걸음마다 backend.chat(stream False)을 부르고, chat 길은 --no-stream(평가 대기열 고정 꼴)이다. smoke 에서 idle 60 끊김 넷이 모두 받은 바이트 0 이었다. 그래서 S 도 M·terminus-2 처럼 "총 시간 상한만"(req_idle_s = req_total_s)으로 둔다. idle 상한을 쓰려면 stewart 평가 길 스트리밍(개발 몫)이 먼저다. O(OpenCode 1.19.5)·P(Pi 1.4.0)는 스트리밍으로 보이며, 설치 smoke 의 요청 기록으로 확정한다. **M(mini 2.4.6)은 비스트리밍**이다. mini 는 응답 전체를 받는 짜임이라 바꾸면 mini 를 고치는 셈이 된다 → M 은 아래 "총 시간 상한만" 꼴로 등록한다(차례 칸 req_idle_s = 600).
   - 평가 대기열 칸: 대기열 맨 위 `req_total_s 600`·`req_idle_s 60`. 차례가 맨 위 값을 덮는다. 끊는 대상은 모델 주소 연결만이고, idle 은 받기 쪽 마지막 바이트 뒤 멈춘 시간이다.
   - **다시 보내기를 맞춘다**(끊김이 조용히 묻히지 않게). S 0(평가 길 기본). M 은 기본 10번을 평가기 mini_run 에서 끈다(v2.0.6 a977ed63…·v1.2.4 5d930314…, 과제 sha 그대로). P 는 기본 retry.enabled true·3번을 어댑터가 settings 로 끈다(peer_run.py pi_setup, meta.overrides.settings). 이 둘(M·P)이 "실행기 전체를 그대로 비교"(§5-7)에서 벗어나는 다시 보내기 손질이다. 까닭은 다시 보내기가 측정 불가를 성공·시간으로 바꿔 셈법을 실행기마다 다르게 만들기 때문이다. 결과 표에 M·P 둘로 적는다. 그 밖의 덮어쓰기는 평가 조건(같은 걸음 상한·망 없음·사용자 설정 안 읽기)이다: O 의 agent.build.steps = max_steps·permission, 망·업데이트·플러그인·홈의 .claude 읽기 끄기, P 의 --offline·-ne -ns -np -na·--no-mcp, 둘 다 HOME = 회차 격리. 모두 회차 meta.overrides 에 남으므로 표 각주 "overrides 칸 참조"로 둔다. O 는 AI SDK 기본 2번[추정]을 끌 손잡이가 없다 → 차례마다 REQCUT 수가 backend_error 회차 수보다 많으면 O 에 "재시도로 끊김 삼킴"을 표시한다.
   - 맞추지 못한 실행기가 있으면 그 실행기는 "총 시간 상한만"으로 등록하고, 대비 표에 표시한다.
   - 실행기 클라이언트 상한은 모두 프록시보다 크게(1800초) 둔다 → 끊는 쪽이 한 곳이다.
   - 프록시 손잡이는 장비 설정 담당 판 손질이다(평가 대기열).
   - 스트리밍이 출력 분포를 바꾸지 않는지 등록 전에 S 한 칸으로 대조한다. v2 32 × 1, 스트림 ↔ 비스트림(탐색).
2. **봉인(기술 강제)**: h1.2 는 처음부터 봉인 자리에서 만들고 돌린다. 등록에 적는 것은 셋이다: 봉인 적용 시각, 읽을 수 있는 주체, 래퍼가 돌려주는 칸(A–D + s6_rerun — 비공개 운영 기록 ①). 보고에는 칸 수준 숫자만 싣고, 과제 ID 별 성공은 봉인 자리에 남긴다.

   - 없는 것: 시작 전 대 보기. 파드 /status 에 `hours_left` 를 더하는 파드 v21 은 도구 담당 몫이다. 평가 대기열의 시작 전 판정은 평가 담당·장비 설정 담당 몫이다(도구 담당 답 ②) [등록 전 확인 7].

## 6. h1.2 크기·배분을 정하는 파일럿(등록 전, 판정에 안 씀)
- 총괄 지시: P-001 의 측정 불가(긴 Q·R 과제의 시간 초과)를 반영해 스트리밍·idle 60초 조건에서 정한다.
- 파일럿 자료: **h1.2 가 아니라 개발 묶음**(v2.0.5 32과제)이다. S·M 두 실행기 × 1회(O·P 어댑터가 그때 되면 넣음). §5-1 프록시 조건이다.
- 볼 것: 범주별(R·G·L·Q·V) 단계 시간 분포, 측정 불가율, 과제 간 분산 σ²_과제.
- 정할 것:
  1. 요청 총 시간 상한 — 범주별 단계 시간 p99 의 1.5배와 max_tokens ÷ 20 tok/s 가운데 큰 쪽(P-001 민감도에서 600초면 충분했다).
  1-1. idle 상한 — `max(60, ⌈1.5 × 첫 토큰 시간 p99⌉)`, 위 끝 600. 첫 토큰 시간은 파일럿 앞뒤로 vLLM /metrics 의 time_to_first_token 막대로 읽는다. 파일럿의 REQCUT idle 비율이 1% 를 넘으면 이 식으로 올린다(평가 담당 제안 그대로 받음).
  1-2. 과제 시간 상한 — 범주별로 정한다. 생각 켬 실측 회차 시간 p95 × 1.5(평가 담당 의견 가)와 1800초 가운데 큰 쪽이다. 파일럿 실행기(S·M) 가운데 큰 값을 쓴다. 모든 실행기에 같은 값을 둔다.
  2. 범주 배분 — v2 비율(R 12·G 4·L 6·Q 8·V 2)을 기본으로 둔다. 파일럿에서 측정 불가율이 5%를 넘는 범주는 과제 길이를 줄인 꼴로 만든다(평가 담당 몫). 빼지는 않는다.
  3. 과제 수 n = (z₀.₉₇₅ + z₀.₈)² · σ²_d / δ². 여기서 σ²_d 는 실행기 간 과제별 차이의 분산, δ = 12%p(32과제 반폭 어림에서 큰 차이만)다. n 은 32 이상으로 하고, 위쪽은 돈 상한(§7)으로 자른다.
- 파일럿 결과와 정한 값은 h1.2 를 만들기 전에 이 초안에 넣는다. 등록은 그 뒤다.
