# stewart 개선 방향 탐구 보고서

2026-11-11 · 사람(제품 주인)

## 요약

stewart 개선은 "재는 자를 먼저 세우고, 남의 실행기에서 배운 것을 범위를 붙여 옮긴다"로 방향을 잡는다. 연구는 그 뒤의 일이고, 아래 내용은 연구가 되지 않더라도 stewart에 그대로 쓰인다.

- **지금 코드**: 문맥 관리, 편집 견고성, 헛돌기 방지, 끝내기 전 검증, 장치별 기록은 갖췄다. 빈 곳은 여섯 군데다.
- **평가**: 기존 벤치는 stewart를 만든 쪽이 함께 짰으므로 우수성의 근거로 쓰지 않는다. 공개 벤치, 기존 실행기 기준선, 고치는 쪽이 못 보는 세트가 필요하다.
- **방법론**: 실행기 × 모델 × 과제 세 축에서 stewart가 동료 실행기에 지는 곳을 분해하고, 원인 장치를 엔진·모델 프로필·스킬 중 맞는 자리에 옮긴다.
- **연구로서**: 노벨티는 조건부 통과다. 같은 구성의 논문은 찾지 못했지만 부품은 모두 선행 연구에 있다.
- **자원**: 2×2×2는 GPU 대여비 $30–270, 3×3×3은 전체 $300–2,000, 기간은 다른 일과 병행하는 기준 10–13주로 어림한다.
- **정한 것**: EXAONE은 쓰지 않는다. 공개 가중치의 작은 모델을 기준으로 한다. 로컬 장비 구매는 2×2×2 결과를 본 뒤 정한다.

## 출발점과 결정

EXAONE 무료 API를 stewart에 붙일 수 있는지에서 시작했고, 붙일 수는 있지만 쓰지 않기로 했다. 연구 내용이 LG 쪽으로 들어가는 것을 원치 않고, 개인 연구자로서 공개 가중치의 작은 모델을 기준으로 삼기로 했기 때문이다.

### EXAONE에서 확인한 사실

- LG AI연구원이 2026-11-09 K-EXAONE 2.5 API를 무료로 열었다([Korea Times](https://www.koreatimes.co.kr/business/companies/20261109/lg-ai-research-opens-k-exaone-25-api-free-of-charge)).
- OpenAI 호환 chat completions이고 모델 이름은 `k-exaone_v2.5`, 텍스트 전용, 최대 문맥 524,288토큰이다([엔드포인트 문서](https://docs.exaone.ai/ko/docs/k-exaone-2.5)).
- 요청 표에 `tools`가 없지만, [에이전트 가이드](https://docs.exaone.ai/ko/docs/agent-start)의 OpenCode 설정에는 `"tools": true`가 있다. 가이드가 다루는 실행기는 Hermes와 OpenCode뿐이고 Pi는 없다.
- 에이전트 용도에는 `preserve_thinking`을 켜라고 권장하고, 추론은 `reasoning_content`로 따로 돌아온다.
- 속도 제한은 초·분·일 단위이고 무료 한도 수치는 공개돼 있지 않다. 사용 분석에 동의하면 일일 한도가 올라간다([Rate Limits](https://docs.exaone.ai/ko/docs/rate-limits)).
- 무제한이 아니고, 무료 종료일과 버전 고정이 없어 재현 근거로 쓰기 어렵다.

### 도구 호출 규격 정리

OpenAI 규격은 통신 형식이지 모델이 실제로 내는 형식이 아니다. 그래서 도구 호출은 클라이언트와 서버 양쪽이 맞아야 동작한다.

1. 클라이언트가 `tools`(JSON Schema로 적은 도구 목록)를 실어 보낸다.
2. 서버가 `tool_calls`를 돌려준다. `arguments`는 객체가 아니라 JSON 문자열이다.
3. 클라이언트가 실행하고 `role: "tool"` 메시지에 `tool_call_id`를 맞춰 결과를 넣는다.

모델의 자체 출력 형식을 이 JSON으로 바꾸는 일은 서버가 한다. vLLM은 `--enable-auto-tool-choice --tool-call-parser`, llama.cpp는 `--jinja`가 그 역할이다. `reasoning_content`는 공식 규격이 아닌 확장 필드다. stewart의 `stewart ping`은 이미 툴콜 1회를 시험한다.

### 정한 것

| 항목 | 결정 |
|---|---|
| EXAONE | 쓰지 않는다 |
| 기준 모델 | 공개 가중치의 작은 모델(24GB 카드에 4비트로 올라가는 급) |
| 실험용 가중치 | 원본 가중치. abliteration 판은 나중 비교 모듈 |
| 문제를 보는 틀 | 실행기 × 모델 × 과제 세 축 |
| 연구의 위치 | 먼 일. 기여가 뚜렷해야 하지만, 못 뽑아도 stewart 개선에 쓰이면 계속한다 |

## stewart 현재 상태

stewart는 최근 실행기 연구의 핵심 장치를 대부분 갖췄고, 특히 장치별 측정 기록이 강점이다. 점검 대상은 공개 stewart 저장소의 커밋 f3be1cb(2026-11-11 14:01)이다.

### 갖춘 것

| 영역 | 코드에서 확인한 내용 | 위치 |
|---|---|---|
| 문맥 관리 | 창의 0.7을 넘으면 오래된 도구 결과를 줄임. 가리기·요약·둘 다·끔을 환경 변수로 비교 가능. 굴러가는 가리기는 arXiv 2508.21433의 M=10을 따름 | compact.py, engine.py |
| 편집 견고성 | 정확 일치 → 줄 번호 떼기 → 느슨한 매칭 순서. 읽지 않았거나 그 사이 바뀐 파일은 쓰기 거부 | tools.py |
| 헛돌기 방지 | 같은 호출 3번이면 경고, 6번이면 중단. 되짚기와 금지 목록 | engine.py, reflect.py, steer.py |
| 끝내기 전 검증 | 확인 명령 실행, 요구 하나씩 대조, 처음부터 실패하던 시험과 새로 깬 시험 구분, 남은 할 일 확인 | selfcheck.py |
| 측정 | 장치가 언제 무엇을 했는지 실행마다 기록. `bench -n`으로 반복 실행 | components.py, cli.py |
| 사람에게 넘기기 | 비밀번호·sudo·로그인에서 막히면 같은 시도를 되풀이하지 않고 사람 손 카드로 넘김 | steer.py, 프로필 지시문 |

도구는 기본 24개이고 정의 분량은 약 8,350자다. `code` 프로필은 이미 13개로 줄여 놨고, `chat` 프로필은 전부를 연다.

## 개선 후보

후보는 바로 할 것 6개, 재 보고 정할 것 7개, 뒤로 둘 것 1개다. 바로 할 것은 빈 곳이 코드에서 확인됐고 고쳐서 손해 볼 일이 없는 것들이다.

### 바로 할 것

| 번호 | 무엇을 | 왜 |
|---|---|---|
| 가-1 | 본문에 쓴 도구 호출을 직접 파싱 | 작은 양자화 모델에서 자주 나는 실수다. 도구 호출을 지원하지 않는 서버에도 붙을 수 있게 된다 |
| 가-2 | 깨진 인자 JSON 복구(끝 쉼표, 코드 울타리, 따옴표) | 다시 요청하는 단계가 줄어든다 |
| 가-3 | 편집 직후 문법 검사와 고친 주변 표시 | 문법을 깨는 편집을 그 자리에서 막는 것은 SWE-agent 연구의 핵심 발견이었다(제 기억에 의한 서술이고 이번에 원문을 다시 확인하지는 않았다) |
| 가-4 | OpenAI 백엔드에 429·5xx 재시도와 속도 조절 | 긴 실행이 중간에 죽지 않게 한다 |
| 가-5 | 추론을 다음 요청에 되돌려 보내기(백엔드별 필드 이름 설정) | 같은 결함이 Hermes에도 이슈로 올라와 있다([#56004](https://github.com/NousResearch/hermes-agent/issues/56004)) |
| 가-6 | Terminal-Bench·SWE-bench 어댑터와 반복 실행 지표 | 기존 실행기와 같은 과제로 맞붙이려면 필요하다 |

### 재 보고 정할 것

근거가 엇갈리거나 모델마다 달라서, 켜고 끄는 손잡이로 넣고 숨긴 세트에서도 오르는 것만 남긴다.

| 번호 | 후보 | 찬성 근거 | 반대 근거 또는 주의 |
|---|---|---|---|
| 나-1 | 해시 줄 편집 | 약한 모델일수록 이득이 커서 한 모델은 6.7%에서 68.3%로 올랐다([The Harness Problem](https://blog.can.ac/2026/02/12/the-harness-problem)) | 구현자 본인의 벤치다. 독립 재현은 편집 형식이 병목이 아니라고 봤다([재현 글](https://dev.to/nwyin/hashline-vs-replace-does-the-edit-format-matter-15n2)). 기존 기록에서 편집 실패율부터 센다 |
| 나-2 | 도구 수 줄이기 | 도구가 적으면 작은 모델이 덜 헷갈린다 | `code`는 이미 13개다. 분량은 과하지 않아 선택 혼란이 쟁점이다 |
| 나-3 | 추론 유지 방식(끔, 도구 호출 차례만, 전부) | 에이전트 용도에 전부 유지를 권장하는 모델이 있다 | 문맥을 빨리 채운다. Qwen은 템플릿에 따라 켜면 도구 호출이 깨진 사례가 있다([기록](https://allanchan339.github.io/bug-fixes/2026/04/29/Qwen36-27B-tool-calling.html)) |
| 나-4 | 요약 때 까닭 보존 | 압축이 지시는 남기고 까닭을 떨어뜨려 결정을 뒤집는 실패 유형이 보고됐다([Model or Harness?](https://arxiv.org/pdf/2607.28802)) | stewart 요약기는 도구 결과를 600자에서 자른다. 제약이 압축 뒤에도 남는지 시험이 필요하다 |
| 나-5 | 읽기 묶음과 앞당겨 넣기 | Dirac이 왕복을 줄여 비용을 낮췄다([토론](https://brianlovin.com/hn/47920787)) | 효과는 주로 속도와 비용이다 |
| 나-6 | 지시문과 도구 설명의 언어(한국어 대 영어) | 근거를 찾지 못한 가설이다 | 재 봐야 안다 |
| 나-7 | 코드로 도구 부르기 | 14개 모델 중 11개에서 JSON 호출과 같거나 나았다([논문](https://arxiv.org/pdf/2608.06370)) | 전부 비공개 API 모델이고, 약한 모델 셋은 줄바꿈을 잘못 써서 실패했다. 우선순위 낮음 |

### 뒤로 둘 것

- **자기 개선 루프**: AHE는 열 번 반복으로 Terminal-Bench 2 점수를 69.7%에서 77.0%로 올렸고, 이득은 지시문이 아니라 도구·미들웨어·장기 기억에서 나왔다([요약](https://www.wizwand.com/paper/69f190c955a3c32af89fbd0d)). 재는 자가 먼저 있어야 한다.

## 평가 문제: 오염과 과최적화

고칠 때 본 과제로 점수를 재면 이득의 절반 이상이 가짜일 수 있다는 것이 여러 연구에서 측정됐다. stewart의 초기 벤치는 stewart를 만든 Claude Code가 함께 짰으므로 같은 위험이 있다.

### 측정된 근거

| 발견 | 수치 | 출처 |
|---|---|---|
| 다듬은 과제 밖으로 전이가 거의 없음 | 조정 45문제에서 진화시킨 실행기가 숨긴 34문제에서 평균 +0.6점 | [Rethinking the Evaluation of Harness Evolution](https://arxiv.org/pdf/2607.12227) |
| 이득의 절반이 과최적화 | 유의한 이득이 난 21개 설정에서 과최적화 몫 평균 54%. 공개 Qwen 모델 9개(0.8B–35B) 포함 | [Harness-Delta Attribution](https://arxiv.org/pdf/2610.22466) |
| 보이는 점수와 숨긴 점수가 따로 움직임 | 같은 방향으로 움직인 비율 53.1%. 같은 커밋도 약 ±4.75점 흔들림 | [HarnessDev](https://arxiv.org/pdf/2609.01437) |
| 만든 모델과 돌리는 모델의 공적응 | Opus가 만든 실행기를 Gemini로 돌리자 SWE-Pro 69.3에서 33.0 | 같은 논문 |
| 실행 환경만으로도 점수가 달라짐 | 자원 설정 차이만으로 Terminal-Bench 2.0에서 6%p | [Anthropic, Infrastructure noise](https://www.anthropic.com/research/infrastructure-noise) |
| 출제자에게 유리한 시험 | 모델이 만든 시험이 그 모델을 1위로 올릴 만큼 편향(번역 과제) | [When LLMs Benchmark Themselves](https://aclanthology.org/2026.emnlp-main.629/) |

### stewart에 적용할 원칙

- 기존 stewart 벤치는 회귀 시험으로만 쓴다. 우수성의 근거로 쓰지 않는다.
- 고치는 세션은 조정용 과제의 실패만 본다. 봉인 세트는 그 세션이 읽지 못하는 곳에 두고, 채점 코드만 접근하며, 통과 개수만 돌려준다.
- 한 번도 안 쓴 공개 벤치를 바깥 기준으로 둔다. 기존 실행기(OpenCode, Pi 등)를 같은 모델로 함께 돌려 기준선을 만든다.
- 모든 측정은 반복 실행하고, 컨테이너 자원 한도와 추론 설정을 조건끼리 똑같이 맞춘다.

### 필요한 표본 크기

기준 통과율 30%, 과제 난이도가 고르지 않다고 가정하고 같은 과제를 두 조건으로 짝지어 비교한 모의실험 결과다. 실제 흔들림은 기준선을 돌려 봐야 확정된다.

| 잡으려는 효과 | 검정력 80%에 필요한 규모 |
|---|---|
| +5점 | 과제 300개 × 3회 |
| +8점 | 과제 90개 × 5회 또는 150개 × 3회 |
| +10점 | 과제 90개 × 3회 |

Terminal-Bench 2.1 하나(89문제)로는 8점 이상만 잡힌다. 선행 연구의 이득이 5–7점대라 공개 벤치 두세 개를 합쳐 200–300문제로 판정해야 한다.

## 선행 연구 지도

세 축을 모두 다룬 연구는 측정에서 멈췄고, 개선까지 간 연구는 축을 둘까지만 쓴다. 실행기만 바꿔도 같은 모델의 Terminal-Bench 2.0 점수가 13.7%p 벌어진 사례가 있어 연구가 몰리는 분야다([서베이](https://arxiv.org/pdf/2606.20683)).

| 갈래 | 대표 연구 | 한 일 | 우리에게 남는 빈칸 |
|---|---|---|---|
| 실행기 자동 진화 | [AHE](https://arxiv.org/html/2604.25850v2), [Self-Harness](https://arxiv.org/pdf/2606.09498), [HarnessCompass](https://arxiv.org/pdf/2608.01918) | 실패 기록을 보고 실행기를 고침. Self-Harness는 Qwen3.5-35B-A3B가 스스로 고쳐 Terminal-Bench 2.0에서 18.0→36.7 | 대부분 같은 벤치 안에서 가름 |
| 숨긴 세트로 합격 판정 | [HarnessBank](https://www.alphaxiv.org/abs/2607.13683), [StarHarness](https://arxiv.org/pdf/2608.24804) | 고칠 안은 모델이, 측정과 검정은 코드가 맡음. 제안자가 못 보는 선택 과제 | 우리 합격 문과 같은 구조라 새롭지 않음 |
| 벤치 밖 과제로 다듬기 | [ModularRSI](https://arxiv.org/pdf/2609.14857), [DarwinX](https://arxiv.org/html/2608.07545v1) | 벤치 문항 없이 다듬어 Terminal-Bench 2.0을 47.57→52.43. DarwinX는 합성 과제로 다듬어 실제 브라우저 과제로 판정 | 과제를 누가 냈는지는 변수로 두지 않음 |
| 도전자가 맞서는 구조 | [CHASE](https://arxiv.org/html/2609.18366v3), [Ctx2Skill](https://arxiv.org/pdf/2604.27660) | CHASE는 벤치의 규약을 바꿔 지름길을 찾음. Ctx2Skill은 도전자가 과제를 내고 스킬을 진화 | 동료 실행기를 도전자로 쓰지 않음 |
| 자기 대결(가중치 학습) | [Self-play SWE-RL](https://icml.cc/virtual/2026/poster/66747) | 한 모델이 버그를 심고 고쳐 SWE-bench Verified +10.4점 | 실행기가 아니라 모델을 학습 |
| 모델끼리 출제 | [LivingArena](https://www.alphaxiv.org/abs/2607.24780) | 서로 상대가 못 풀 문제를 냄 | 질의응답 중심, 에이전트 과제 아님 |
| 세 축 측정 | [Harness-Bench](https://arxiv.org/html/2605.27922), [Finding the Right Fit](https://arxiv.org/html/2610.00917v1), [When Agents Fail](https://arxiv.org/abs/2610.32483) | 실행기 × 모델 × 과제를 교차 측정. 가장 잘 맞는 실행기가 모델과 벤치에 따라 바뀜 | 개선은 하지 않음. Right Fit의 설계 제안은 "검증되지 않은 제안" |
| 남의 실행기에서 배우기 | [RiseHarness](https://arxiv.org/html/2610.27435) | 다른 실행기의 구현을 검색해 한 실행기에 옮기고 못 본 벤치로 확인. 외부 참조를 빼면 Pass@1 5.5% 하락 | 다른 실행기를 돌리지는 않고 코드와 문서만 가져옴 |
| 여러 실행기의 상보성 | [Harness-S](https://arxiv.org/html/2611.04277) | 실행기마다 푸는 과제가 다르다는 성질을 모델 학습에 씀 | 실행기 하나를 키우는 데 쓰지 않음 |
| 여러 벤치·모델 동시 진화 | [HarnessX](https://arxiv.org/pdf/2606.14249), [여러 과제 자기 진화](https://arxiv.org/html/2609.38372v1) | HarnessX는 모델-벤치 조합 15개를 다룸. Opus가 다듬어 Qwen3.5-9B의 SWE-bench Verified 23.6→41.8 | 조합마다 따로 진화. 남의 실행기를 보지 않음 |

우리 모델 계열에는 여지가 크다. Harness-Bench에서 실행기 간 점수 편차가 다른 모델은 1.4–3.0인데 우리 모델 계열(Qwen 계열 — 판 이름 가림)은 14.64였다.

### 비어 있는 자리

- 세 축의 실측 결과로 무엇을 옮길지 고르고, 실행기 하나를 개선해, 숨긴 벤치로 확인하는 연구.
- 과제를 누가 냈는지(자기, 동료, 기계적 생성)를 변수로 둔 비교.
- 실행기를 고친 모델과 시험을 낸 모델이 같은 계열일 때 이득이 부풀려지는지의 통제 실험.

## 방법론: 격차를 축별로 쪼개고 범위를 붙여 옮긴다

stewart가 동료 실행기에 지는 정도를 모델 축과 과제 축으로 분해하고, 성분마다 원인 장치를 찾아 맞는 자리에 옮긴다. 핵심 원칙은 "한 축에 조건을 걸려면 다른 축에서는 일반적이어야 한다"이다.

### 절차

1. **표를 채운다.** stewart는 모든 (모델 × 과제 종류) 칸을 넉넉히 반복한다. 동료 실행기는 얕게 훑은 뒤 stewart가 지는 칸만 더 돌린다.
2. **격차를 분해한다.** 칸마다 "가장 잘한 동료 − stewart"를 구해 아래 식의 네 성분으로 나눈다.
3. **성분마다 대조 진단을 한다.** 그 성분에 가장 크게 기여한 과제에서 두 실행기의 궤적이 갈라지는 지점을 찾고, 원인 장치와 그 범위를 기록한다.
4. **범위별 규칙으로 받아들인다.** 고치는 쪽이 못 보는 선택 세트에서 판정한다.
5. **세 방향으로 숨겨서 판정한다.** 본 종류의 못 본 과제, 못 본 과제 종류(다른 기존 벤치), 못 본 모델.

```latex
g_{m,t} = \max_{p \in \text{peers}} y_{p,m,t} - y_{s,m,t}, \qquad g_{m,t} = \mu + \alpha_m + \beta_t + \varepsilon_{m,t}
```

여기서 y는 통과율, s는 stewart, m은 모델, t는 과제 종류다.

### 성분과 고칠 자리

| 성분 | 뜻 | stewart에서 고칠 자리 | 받아들이는 조건 |
|---|---|---|---|
| μ (전체 평균) | 어디서나 지는 일반 결함 | 엔진 본체 | 어느 칸도 잡음 이상으로 나빠지지 않을 것 |
| α (모델 성분) | 특정 모델에서만 짐 | 모델별 프로필 | 그 모델에서 과제 종류 둘 이상에 걸쳐 도움이 될 것 |
| β (과제 성분) | 특정 과제 종류에서만 짐 | 필요할 때 불러오는 스킬 | 그 과제 종류에서 모델 둘 이상에 걸쳐 도움이 될 것 |
| ε (잔차) | 특정 조합에서만 짐 | 옮기지 않음 | 과최적화로 보고 버림 |

stewart에는 엔진, 프로필, 스킬이 이미 갈라져 있어 구조를 새로 만들 필요가 없다.

### 틀릴 수 있는 예측

"전역으로 표시된 장치는 못 본 모델과 못 본 과제 종류에서도 이득이 남고, 조건부 장치는 남지 않는다." 범위 표시가 전이를 예측하면 방법론이 성립한다. 예측하지 못하면 축 분해가 쓸모없다는 결론이 된다.

비교군은 같은 예산에서 두 가지다.

- 축을 무시하고 전부 합쳐 평균으로만 받아들이기
- 칸마다 따로 특화하기

### 위험

- 동료가 stewart를 이기는 칸이 없으면 신호가 없다. 그 경우 자기 실패 기록 기반으로 돌아간다.
- 2×2×2로는 분해가 거칠다. 파이프라인 확인과 잡음 측정용이고, 예측 검증은 3×3×3에서 한다.
- 동료의 장치가 그 실행기 구조에 묶여 있으면 원리만 가져와 다시 구현해야 한다.
- 축은 더 있다(누가 고치는가, 양자화 수준). 이들은 고정한다.

### 곁가지로 내린 것

- **교차 출제**: 실행기+모델 조합이 서로 과제를 내는 구성. 버그 심기로 통일하고, 저장소에 원래 있던 시험으로 판정하며, 코드가 유효성을 거른다. 새 과제가 계속 필요해질 때 봉인 세트 공급원으로 쓴다.
- **제안자-출제자 결합 실험**: 고친 모델과 출제한 모델이 같은 계열일 때 이득이 부풀려지는지 보는 2×2. HarnessDev가 비슷한 결합을 이미 재서 우선순위를 내렸다.

## 노벨티 판정

판정은 조건부 통과다. 세 축을 모두 쓰면서 실행기 하나를 개선하고 범위 표시가 전이를 예측하는지까지 검증한 논문은 찾지 못했지만, 부품은 모두 선행 연구에 있다.

### 가장 가까운 연구와 차이

| 연구 | 겹치는 부분 | 빠진 부분 |
|---|---|---|
| [RiseHarness](https://arxiv.org/html/2610.27435) | 다른 실행기의 장치를 한 실행기에 이식, 못 본 벤치로 확인 | 다른 실행기를 돌린 결과로 고르지 않음. 과제 종류 하나 |
| [Finding the Right Fit](https://arxiv.org/html/2610.00917v1) | 세 축 표, 같은 과제·같은 모델에서 실행기 대조 | 진단까지만. 개선과 검증이 없음 |
| [HarnessX](https://arxiv.org/pdf/2606.14249) | 여러 모델과 벤치에서 개선 | 조합마다 따로 진화. 못 본 과제 평가 없음 |
| [Agent Evaluation Reliability](https://alphaxiv.org/abs/2610.00651v1) | 모델·과제·실행기·벤치로 점수 분산을 분해 | 순위 신뢰도 측정이 목적. 개선에 쓰지 않음 |

### 조건이 붙는 이유

- **전문을 못 읽은 근접 연구가 있다.** [EvolveNet](https://arxiv.org/abs/2608.04968)은 수정에 범위 유형을 붙여 병합하는데 우리 "범위 표시"와 개념이 가깝다. Object-Oriented Harness는 과제 종류별 특화와 분배기를 다룬다. DarwinX 부록도 남아 있다.
- **검색으로 "없다"를 증명할 수 없다.** 이 분야는 매주 논문이 나온다. RiseHarness는 3주 전, Harness-S는 5일 전에 나왔다.
- **새것은 조합과 예측이다.** "새 조합일 뿐"이라는 평을 받을 수 있고, 방어 수단은 틀릴 수 있는 예측 하나다.
- **"작은 공개 모델"은 기여로 내세우지 않는다.** 플랫폼 공백은 기여가 아니라는 기준에 따른다.

### 탐구 중에 선점이 확인돼 내려놓은 주장

- "벤치를 안 보고 다듬어 공개 벤치로 재기"는 ModularRSI와 DarwinX가 먼저 했다.
- "도전자가 실행기와 함께 진화"는 CHASE와 Ctx2Skill이 먼저 했다.
- "작은 공개 모델에서의 과최적화 측정"은 Harness-Delta Attribution이 먼저 했다.
- "강한 모델이 작은 모델용 실행기를 다듬기"는 HarnessX가 먼저 했다.

### 대응

근접 연구 세 편을 읽은 뒤 사전 등록서를 날짜가 남는 곳에 공개해 선점을 방어하고, 투고 직전에 한 번 더 확인한다.

## 실험 구성과 자원

추천은 단계적 혼합이다. 2×2×2를 대여로 먼저 돌려 처리량과 흔들림을 실측하고, 그 수치로 3×3×3 규모와 로컬 장비 구매를 정한다. 아래 수치는 모두 어림이고 가정을 함께 적었다.

### 3×3×3 구성안

| 축 | 구성 | 비고 |
|---|---|---|
| 모델 | Qwen 계열 27B(판 이름 가림), Gemma 4 31B, 셋째(Muse Glimmer 30B 또는 Devstral Small 2) | 24GB 카드에 4비트로 올라가는 서로 다른 계열. 셋째는 직접 검증하지 못한 후보 |
| 숨긴 모델 | gpt-oss-20b | 진단에 쓰지 않고 판정에만 사용 |
| 실행기 | stewart(타깃), OpenCode, Pi. 예비 OpenHands | OpenCode는 최근 교차 평가에서 모델 전반 1위, Pi는 최소 구성의 대조군 |
| 과제 종류 | 터미널 작업, 저장소 버그 수정, 사무·데이터 작업 | 판정용으로 네 번째 종류 하나를 숨김 |

Qwen 계열 27B(판 이름 가림)는 제작사 수치로 Terminal-Bench 2.1에서 73.0이다. 차이가 보이도록 통과율이 30–70% 구간에 드는 과제를 골라야 한다. Right Fit 논문이 OpenHands와 Pi의 어댑터와 평가 코드를 공개해 두어 연결 작업을 줄일 수 있다.

### GPU와 예산

24GB급 카드 여러 장이면 된다. 같은 양자화 가중치면 결과는 카드 종류와 무관하다. GPU 한 장이 시간당 10–40회를 처리한다고 가정했다.

| 단계 | 실행 횟수 | GPU 시간 | GPU 비용 |
|---|---|---|---|
| 2×2×2 | 약 5,300 | 130–530 | $30–270 |
| 3×3×3 | 약 28,000 | 700–2,800 | $150–1,400 |

- 단가는 빌린 GPU 3090 기준 커뮤니티급 $0.22, 보안급 $0.50으로 잡았다(대여처 가격표 — 대여처 이름 가림). 이 실험은 공개 벤치만 쓰므로 보안급이 아니어도 된다.
- 처리량은 서빙 구성에 좌우된다. 기본 vLLM은 합계 200–300 tok/s, HyperQwen 패치는 짧은 요청 64개 동시 기준 약 1,035 tok/s로 보고된다(제3자 저장소 — 저장소 이름에 모델 판 이름이 있어 링크 가림).
- 과제 컨테이너를 돌릴 x86 서버가 따로 필요하다. 로컬 맥은 ARM이라 맞지 않고, 로컬 x86 장비는 동시 5개 정도라 3×3×3에 두 달 가까이 걸린다. CPU 클라우드 비용은 수백 달러로 예상하지만 확인하지 못한 어림이다.
- 전체로는 3×3×3까지 $300–2,000, 중간값 $600–1,200로 본다.

### 기간

다른 일과 병행하는 기준 약 10–13주다. GPU 8장이면 실행 자체는 4–15일이고, 병목은 진단과 이식에 드는 사람 시간이다.

| 단계 | 기간 |
|---|---|
| 준비(어댑터, 동료 실행기 연결, 사전 등록) | 2–3주 |
| 2×2×2 | 1주 |
| 3×3×3 표 | 1–2주 |
| 진단과 이식 반복 | 3–4주 |
| 최종 판정과 정리 | 3주 |

### 대여와 로컬 구축

## 형식 이론화 가능성

이론으로 정립할 수 있지만, 맞는 도구는 증명 중심의 형식 기법이 아니라 통계적 정식화다. 측정 쪽은 이미 그렇게 정식화한 연구가 있고, 개선 쪽에 쓰는 것이 비어 있다.

| 틀 | 무엇을 정식화하나 | stewart에서의 쓸모 | 근거 |
|---|---|---|---|
| 일반화 가능성 이론(교차 혼합모형) | 점수를 모델·과제·실행기와 그 상호작용의 분산 성분으로 분해 | "범위"를 장치 효과가 어느 항에 실리는가로 정의. 필요한 과제 수와 반복 수를 계산 | [Agent Evaluation Reliability](https://alphaxiv.org/abs/2610.00651v1)가 순위 신뢰도 측정에 적용 |
| 적응적 데이터 분석 | 숨긴 세트를 여러 번 물어도 그 세트에 과최적화되지 않을 조건 | 합격 문의 답에 문턱과 잡음을 넣어, 몇 번까지 물어도 되는지 보장 | [Dwork 외, 재사용 가능한 숨긴 세트](https://arxiv.org/pdf/1506.02629) |
| 인과 추론의 전이 가능성 | 한 집단에서 잰 효과가 다른 집단으로 옮겨 가는 조건 | "전역 장치는 못 본 모델에서도 통한다"는 예측을 가정과 함께 적는 언어 | 배경 지식. 이번에 출처를 확인하지 않음 |
| 요인 실험 설계 | 상호작용이 드물다는 가정 아래 일부 조합만 돌려 추정 | 정육면체를 다 채우지 않는 근거 | 배경 지식. 이번에 출처를 확인하지 않음 |
| 형식 기법(모델 검사, 증명) | 실행기와 절차가 지켜야 할 불변식 | "고치는 세션으로 봉인 세트 내용이 흐르지 않는다", "읽지 않은 파일은 쓰지 않는다" 같은 성질 | 성능 향상은 증명 대상이 아님 |

### 세 축 모형

첫 번째 틀을 우리 문제에 적으면 다음과 같다. 장치 하나를 켜는 것은 이 식에 항을 하나 더하는 일이고, 그 항이 모델이나 과제 종류에 따라 달라지는지가 곧 "범위"다.

```latex
\operatorname{logit} P(\text{pass}_{h,m,t,i}) = \mu + a_h + b_m + c_t + (ab)_{hm} + (ac)_{ht} + (bc)_{mt} + (abc)_{hmt} + u_{i(t)}
```

여기서 h는 실행기, m은 모델, t는 과제 종류, i는 과제 하나다.

### 판단

- **쓸 만한 것은 앞의 두 틀이다.** 혼합모형은 격차 분해와 표본 계산을 어림에서 계산으로 바꿔 주고, 재사용 가능한 숨긴 세트는 합격 문 구현에 바로 들어간다.
- **"이 방법이 성능을 올린다"는 증명할 수 없다.** 얻을 수 있는 것은 조건부 보장이다. 예를 들어 숨긴 세트 크기와 질의 횟수가 주어지면 과최적화의 상한을 말할 수 있다.
- **증명 중심 형식 기법은 성능이 아니라 안전 쪽에 맞는다.** 예전에 기여를 찾기 어려웠던 그 방향이다. 다만 봉인 세트의 정보 흐름 차단은 작게 다룰 만한 소재다.
- 세 번째와 네 번째 틀은 제 배경 지식에 의한 서술이라, 실제로 쓸 때 원전을 확인해야 한다.

## 다음 걸음

연구 여부와 무관하게 가치가 있는 것부터 한다. 1–3번은 GPU 없이 가짜 서버 시험으로 구현할 수 있고, 4번부터 모델 서버가 필요하다.

1. **백엔드 재시도와 추론 되돌려 보내기**(가-4, 가-5). 긴 실행과 생각 켠 모델의 전제 조건이다.
2. **본문 도구 호출 파싱과 인자 복구**(가-1, 가-2). 작은 양자화 모델에서 단계 낭비를 줄인다.
3. **편집 직후 되먹임**(가-3).
4. **반복 실행 지표와 표준 벤치 어댑터**(가-6). 여러 번 중 몇 번 통과했는지를 기록하고, 공개 벤치에서 stewart·OpenCode·Pi의 기준 점수를 잰다. 밤에 걸어 둘 긴 테스트다.
5. **2×2×2**. 대여처가 정해진 뒤 시작한다. 처리량, 흔들림, 동료가 stewart를 이기는 칸이 있는지를 실측한다.
6. **재 보고 정할 후보를 손잡이로 넣기**(나-1–7). 봉인 세트에서도 오르는 것만 남긴다.
7. **3×3×3 진행 여부와 로컬 장비 구매 결정**. 5번 결과를 보고 정한다.
