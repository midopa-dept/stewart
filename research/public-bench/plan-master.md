### (b-2) 로컬 장비 여력(로컬 장비 담당 답, 비공개 운영 기록)
- 로컬 장비는 4코어 8스레드 CPU·램 32GB 이고, VM 몫은 6스레드·약 24GB 다.
- Docker VM 1대(컨테이너 동시 4 안정, 6 상한)를 켠다. 한계가 CPU 라 돈으로 못 넘는다.
- 벤치 VM: 사람 손 한 줄(30–60분)이 남았다.
  - 12단계 이후는 실물로 한 번도 안 돌았다(넘어지면 resume 으로 수 분).
  - **로컬 맥의 벤치 운영 래퍼가 아직 없다** → 벤치 VM 이 선 뒤 장비 설정 담당의 설치 묶음이 한 번 더 든다.
  - 나가는 망은 허용 목록 프록시(37줄)다.
  - 파드 전달은 대상 하나다(GPU 여러 대면 손질).
- 로컬 장비 몫은 **기준 실행·실패 재현·작은 표본**이다. 넓게·빠르게는 빌린 장비에서 과제를 돌린다(로컬 장비 담당 의견, 연구 담당도 같은 판단).

### (b-3) 과제 실행 장비를 어디서 빌리나 — [조사·도구 담당 답 뒤 확정]
| 길 | 무엇이 되나 | 새로 드는 것(품) |
|---|---|---|
| 빌린 GPU 의 **VM 형** 인스턴스(GPU 포함) | 같은 장비에서 서빙 + Docker 과제(TB·SWE 꼴) | 도구 담당: 래퍼에 VM 형 검색·역할, VM 첫 각본(boot.sh 받기·대조), VM 안 Docker 울타리 — 반나절–하루 + 시험 약 $1(11-12 도구 담당 답). 새 제공자·계정은 아님 |
| 다른 제공자의 **CPU 서버**(Docker 됨) + 지금 GPU 파드 | 과제는 CPU 서버, 모델은 파드 | **새 제공자·새 계정·새 망 허용 → 사람 승인 + 장비 설정 담당의 설치 묶음**. 두 빌린 장비 사이 연결(CPU 서버 → 파드)은 빌린 장비끼리라 로컬 쪽 규칙과 무관하다. 다만 키·주소 관리가 는다 |

- **연결 꼴(모든 길 공통)**: 로컬 → 빌린 장비로 나가는 연결만 쓴다. 빌린 장비는 로컬로 연결을 열지 않는다. 결과 묶음은 로컬에서 끌어온다(pull). 모델 요청은 빌린 장비 안에서 끝나거나(VM 형 한 대), 빌린 장비끼리 오간다.
- **연구 담당 권고**: 빌린 GPU 의 VM 형부터 본다. 새 제공자·계정이 들지 않고, 서빙과 과제가 한 장비라 연결이 가장 단순하다. 도구 담당 몫 반나절–하루가 이 계획의 가장 큰 고침이다.

### (b-4) 첫 걸음 — 환경이 필요 없는 벤치부터(총괄 지시)
- 고정 말뭉치 QA 처럼 **GPU 만으로 도는 벤치**는 Docker·VM·벤치 VM 없이 지금 파드에서 바로 돈다. 조사가 오면 (a) 표의 맨 앞에 이 줄을 세운다.
- 이 벤치들은 모델 능력을 잰다. 실행기 기능(stewart 의 도구·넛지)을 재는 몫은 작다. 그래서 Q-B(생각 양)·Q-D(웹 조사 가운데 고정 말뭉치로 되는 몫)에 맞는다. Q-A(기능 수준)는 TB 꼴이 필요하다.

## 조사 2(웹 검색·조사) 반영 — 판 0.5 ([survey-web-research.md](survey-web-research.md))
### Q-C·Q-D 의 벤치: BrowseComp-Plus(주) + OverSearchQA·When2Call(도구 결정 보조)
- **BrowseComp-Plus 를 고르는 까닭**
  - 830문항, 고정 말뭉치(문서 10만)다. 재현되고 오염이 적다. 유출 페이지가 검색에 잡히지 않는다.
  - 공식 채점은 로컬 Qwen3-32B 라 유료 API 가 필요 없다.
  - 난도가 맞다(Qwen3-32B 10.4%, 30B 조사 특화 44.5–54.8%).
  - 무엇보다 **정답 문서를 다 주면 83% 인데 검색을 0.92번만 해서 10%** — 약점이 실행기가 바꿀 수 있는 검색 행동이다. 대화 자리·웹 넛지·생각 양의 효과가 그대로 보인다.
- **stewart 를 고치지 않고 붙이는 길(연구 담당 제안)**
  - stewart 의 web_search 는 SearXNG 주소(STEWART_SEARXNG_URL)로 간다. 그래서 **말뭉치 검색기(BM25 또는 Qwen3-Embed)를 SearXNG 응답 꼴로 내는 작은 가짜 SearXNG**를 세운다.
  - 결과 URL 은 `corpus://<문서 id>` 같은 꼴로 내고, web_fetch 가 그 URL 을 받으면 문서를 돌려주는 가짜 fetch 끝점을 둔다.
  - 그러면 stewart 코드·지시문은 그대로이고, "검색 횟수·검색 0회 비율·읽은 문서 id(정답 문서 재현율)"가 우리 기록에 그대로 남는다.
  - web_fetch 가 임의 스킴을 받는지, 주소 허용 규칙에 걸리는지는 [모름]이다 — 개발 담당에게 묻는다. 안 되면 http://<가짜 주소>/doc/<id> 꼴로 한다.
- **칸(최소)**: chat(moderato) 웹 넛지 끔 · 켬 + talk(대화 자리, 웹 조사 스킬 포함) — 셋 × 표본 200문항 × 1회 = 600회.
  - 생각 양은 창 2 결과로 고른 값 하나로 고정한다. 칸을 늘리지 않는다.
  - 부지표: 문항당 검색 횟수, 검색 0회 비율, 읽은 문서 수, 정답 문서 재현율.
- **장비·돈** [추정, 조사 2 의 어림 × 1.37]
  - 문항당 약 4분 × 600회 = 40 GPU시간이다. 4장 한 대(동시 16)면 약 3h 다. 그러나 문맥이 수만 토큰이라 동시 수를 낮출 수 있다 → 3–5h.
  - 4장 $1.07/h × (3–5h) × 1.37 ≈ **$4.4–7.3**.

  - **Docker·벤치 VM 이 필요 없다** → (b-4) 첫 걸음 줄에 맞는다.

  - SearXNG 대량 검색은 약관상 회색이고 하루 안에 막힐 수 있다.
  - 재현이 안 된다(답·링크가 변함).
  - 채점이 유료다(GPT-4.1·GPT-5.4-mini → 바깥 유료 모델 승인).
  - 한국어 실사용 확인용으로 작은 표본(K-BrowseComp 50문항, 검색 결과 녹화)만 뒤 단계에 둔다.

## BrowseComp-Plus 붙이기 — 개발 담당 답(비공개 운영 기록, 코드 읽기로 답함·돌려 확인은 안 함)

- ② web_fetch 는 **사설·localhost·CGNAT 주소를 못 받는다**(SSRF 막기라 일부러 그렇다). 길 셋:
  - (가) 본문을 검색 결과 content 에 싣는다 → 300자 한계라 다단계 조사에 모자란다. **안 된다.**
  - (나) **공인 주소에 문서 서버**를 둔다 → 빌린 파드의 공인 포트에 문서 서버를 띄우면 stewart 코드를 바꾸지 않는다. 다만 평가 대기열 울타리가 그 공인 주소를 허용하는지는 [모름]이다(평가 담당 확인). 문서를 공인 포트에 내놓는 것은 말뭉치가 공개 자료라 문제가 작다.
